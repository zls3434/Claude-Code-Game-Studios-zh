# Agent Test Spec：systems-designer

## Agent 摘要
**拥有的领域：** 战斗公式、进度曲线、制作配方、状态效果交互、经济数学、数值平衡。
**不拥有：** 叙事和背景故事（narrative-director）、视觉设计（art-director）、代码实现（lead-programmer）、概念性机制规则（game-designer — 协作）。
**Model tier：** Sonnet（单个系统分析 — 公式审查和平衡数学）。
**处理的 Gate ID：** 关于公式和平衡规范的系统审查裁决（使用 APPROVED / NEEDS REVISION 词汇）。

---

## 静态断言（结构性）

通过阅读 agent 的 `.claude/agents/systems-designer.md` frontmatter 验证：

- [ ] `description:` 字段存在且领域特定（引用公式、进度曲线、平衡数学、经济 — 非泛化描述）
- [ ] `allowed-tools:` 列表以读取为主；如项目使用公式评估脚本则可包含 Bash；未经委托，不得在 `design/balance/` 之外写访问
- [ ] Model tier 按 coordination-rules.md 为 `claude-sonnet-4-6`
- [ ] Agent 定义不声称对叙事、视觉设计或概念性机制规则所有权拥有权限

## 测试用例

### Case 1：域内请求 — 适当的输出格式
**Scenario：** 一个伤害公式被提交审查：`damage = base_attack * (1 + strength_modifier * 0.1) - defense * 0.5`，定义范围为 base_attack [10–100]、strength_modifier [0–20]、defense [0–50]。该公式在所有有效输入范围内产生正伤害，平滑缩放，且在定义值范围内无除零或溢出风险。
**预期：** 返回 `APPROVED`，附理由确认公式在设计参数内平衡，在整个输入范围内产生有效输出，且没有退化案例。
**断言：**
- [ ] 裁决恰好为 APPROVED / NEEDS REVISION 之一
- [ ] 理由展示跨输入范围的验证（min/max 案例已检查）
- [ ] 输出保持在系统领域内 — 不评论该机制是否有趣或如何实现
- [ ] 裁决清晰标有上下文（例如"Formula Review: APPROVED"）

### Case 2：领域外请求 — 重定向或升级
**Scenario：** 编剧请 systems-designer 草拟一个奖励玩家稀有制作原料的支线任务的任务脚本。
**预期：** Agent 拒绝编写任务脚本内容，并重定向到 writer 或 narrative-director。
**断言：**
- [ ] 不编写任务叙事内容或对话
- [ ] 明确命名 `writer` 或 `narrative-director` 为正确的处理者
- [ ] 可备注奖励的系统影响（例如"按制作经济模型，此原料应足够稀有以有分量"），但将所有脚本编写转交叙事团队

### Case 3：Gate 裁决 — 正确的词汇
**Scenario：** 一个伤害缩放公式被提交：`damage = base_attack * level_multiplier`，其中 `level_multiplier = (player_level / enemy_level) ^ 2`。在最大 player 等级（50）对最小等级敌人（1）时，倍率为 2500x — 从 10 base attack 武器产生 25,000+ 伤害，远超任何有意义的平衡界限。这是满级时的退化案例。
**预期：** 返回 `NEEDS REVISION`，具体识别退化案例：在满级对最小敌人时，公式产生 2500x 倍率，破坏任何平衡上限。
**断言：**
- [ ] 裁决恰好为 APPROVED / NEEDS REVISION 之一 — 非自由文本
- [ ] 理由包含具体的退化输入值（player level 50, enemy level 1）和结果输出（2500x 倍率）
- [ ] 识别导致问题的具体公式组件（平方比率）
- [ ] 建议至少一种修正方法（例如限制比率、使用对数缩放），而不强制指定选择

### Case 4：冲突升级 — 正确的父级
**Scenario：** game-designer 希望使用简单的 2 变量伤害公式以提高玩家可读性。systems-designer 认为带元素交互的 6 变量公式对于战斗系统的深度是必要的。双方无法在正确的复杂度级别上达成一致。
**预期：** systems-designer 清晰呈现权衡 — 6 变量系统的调优粒度 vs. 2 变量系统的玩家可读性 — 并升级到 creative-director 进行玩家体验裁决。关于「公式对玩家应多复杂」的问题是玩家体验问题，而非纯数学问题。
**断言：**
- [ ] 用具体示例呈现两种方法的权衡
- [ ] 升级到 `creative-director` 进行玩家体验裁决
- [ ] 不单方面在 game-designer 反对的情况下推行 6 变量公式
- [ ] 保持可用，以实施被批准的任何复杂度级别

### Case 5：上下文传递 — 使用提供的上下文
**Scenario：** Agent 收到一个 gate 上下文块，其中包含当前平衡数据：敌人 HP 值范围从 100 到 10,000；玩家攻击值范围从 15 到 150；目标击杀时间在平衡对决中为 8–12 秒；当前公式正在审查中。一个提议的修正公式被提交。
**预期：** 评估将提议的公式代入提供的平衡数据运行（最小和最大输入对、平衡对决场景）并验证击杀时间是否落在 8–12 秒目标窗口内。引用所提供数据中的具体数字。
**断言：**
- [ ] 使用所提供平衡数据中的具体 HP 和攻击值范围
- [ ] 至少计算或估计一个平衡对决场景的击杀时间
- [ ] 对照提供的 8–12 秒目标窗口验证结果
- [ ] 不给泛化的平衡建议 — 所有断言使用提供的数字

## 协议合规性

- [ ] 仅使用 APPROVED / NEEDS REVISION 词汇返回裁决
- [ ] 停留在声明的系统和公式领域内
- [ ] 将玩家体验复杂度权衡升级到 creative-director
- [ ] 不做出有约束力的叙事、视觉、代码实现或概念性机制决策
- [ ] 提供具体的公式分析，而非主观设计意见

## 覆盖说明
- 进度曲线审查（XP 曲线、升级缩放）未涵盖 — 应添加专用案例。
- 经济模型审查（资源产出和消耗率、通胀预防）未涵盖。
- 状态效果交互矩阵（堆叠规则、优先级、免疫交互）未涵盖。
- 跨系统公式依赖审查（例如输入战斗公式的制作公式）未涵盖 — 推迟到集成测试。
