# Agent Test Spec：game-designer

## Agent 摘要
**拥有的领域：** 核心循环设计、进度系统、战斗机制规则、经济设计、面向玩家的规则和交互。
**不拥有：** 代码实现（lead-programmer / gameplay-programmer）、视觉艺术（art-director）、叙事设定和故事（narrative-director — 协调合作）、平衡公式数学（systems-designer — 协作）。
**Model tier：** Sonnet（单个系统设计编写和审查）。
**处理的 Gate ID：** 关于机制规范的设计审查裁决（无命名的 gate ID 前缀 — 使用 APPROVED / NEEDS REVISION 词汇）。

---

## 静态断言（结构性）

通过阅读 agent 的 `.claude/agents/game-designer.md` frontmatter 验证：

- [ ] `description:` 字段存在且领域特定（引用核心循环、进度、战斗规则、经济、面向玩家的设计 — 非泛化描述）
- [ ] `allowed-tools:` 列表以读取为主；包含 Read 用于 GDD 和设计文档；除非设计工具需要，不包含 Bash
- [ ] Model tier 按 coordination-rules.md 为 `claude-sonnet-4-6`
- [ ] Agent 定义不声称对代码实现、视觉艺术风格或独立叙事设定决策拥有权限

## 测试用例

### Case 1：域内请求 — 适当的输出格式
**Scenario：** 一份关于「基于耐力的闪避」系统的机制规范被提交审查。该规范定义：玩家有一个耐力池（100 单位），每次闪避消耗 25 耐力，耐力在不闪避时以 20 单位/秒恢复，闪避给予 0.3 秒无敌。核心循环交互清晰描述，规则无歧义，边缘情况（耐力为 0、恢复期间闪避）已处理。
**预期：** 返回 `APPROVED`，附理由确认核心循环清晰度、无歧义规则和边缘情况覆盖。
**断言：**
- [ ] 裁决恰好为 APPROVED / NEEDS REVISION 之一
- [ ] 理由引用具体的设计质量标准（清晰规则、边缘情况覆盖、核心循环一致性）
- [ ] 输出保持在设计范围内 — 不评论如何在代码中实现或需要什么美术资产
- [ ] 裁决清晰标有上下文（例如"Mechanic Spec Review: APPROVED"）

### Case 2：领域外请求 — 重定向或升级
**Scenario：** 团队成员请 game-designer 编写为什么游戏世界中存在耐力系统的世界内叙事设定解释（例如角色在游戏世界中具有耐力限制的叙事原因）。
**预期：** Agent 拒绝编写叙事/叙事设定内容，并重定向到 writer 或 narrative-director。
**断言：**
- [ ] 不编写叙事或叙事设定内容
- [ ] 明确命名 `writer` 或 `narrative-director` 为正确的处理者
- [ ] 可备注叙事设定应支持的设计意图（例如"耐力系统应强化物理现实主义主题"），但将编写转交叙事团队

### Case 3：Gate 裁决 — 正确的词汇
**Scenario：** 一份关于「环境危险伤害」的机制规范被提交。该规范定义了三种危险类型（火、酸、电），但未指定玩家同时受到多个危险类型影响时会发生什么、在闪避无敌窗口期间施加危险时会发生什么、以及伤害频率是多少（每秒、每 tick、进入时）。
**预期：** 返回 `NEEDS REVISION`，具体识别未定义的边缘情况：多重危险交互、无敌期间危险、以及伤害频率规范。
**断言：**
- [ ] 裁决恰好为 APPROVED / NEEDS REVISION 之一 — 非自由文本
- [ ] 理由按名称识别具体缺失的边缘情况
- [ ] 不拒绝整个机制 — 识别需要填补的具体缺口
- [ ] 提供关于需要定义什么的可操作指导（而非如何实现）

### Case 4：冲突升级 — 正确的父级
**Scenario：** systems-designer 提出一个带有 6 变量和复杂缩放交互的伤害公式，认为这能产生最佳的调优粒度。game-designer 认为该公式对玩家来说太复杂，难以理解，希望使用更简单的 2 变量版本。
**预期：** game-designer 拥有概念性规则和玩家体验意图（「伤害应对玩家可理解」），但将公式粒度问题转交 systems-designer。如果双方无法自行解决分歧（一方想要复杂，一方想要简单），升级到 creative-director 进行玩家体验裁决。
**断言：**
- [ ] 清晰陈述玩家体验意图（直观伤害、玩家自主权）
- [ ] 将公式粒度决策转交 `systems-designer`
- [ ] 将未解决的分歧升级到 `creative-director` 进行玩家体验仲裁裁决
- [ ] 不单方面向 systems-designer 推行某一公式结构

### Case 5：上下文传递 — 使用提供的上下文
**Scenario：** Agent 收到一个 gate 上下文块，其中包含游戏的三个支柱：「玩家创作权」「后果持久性」和「世界响应性」。一份关于「永久死亡与传承加成」的新机制规范被提交审查。
**预期：** 评估将该机制与所有三个提供的支柱对比评估 — 永久死亡如何支持玩家创作权、传承加成如何表达后果持久性、以及世界如何响应玩家死亡？在理由中直接使用支柱词汇。
**断言：**
- [ ] 在评估中按名称引用所有三个提供的支柱
- [ ] 明确评估该机制对每个支柱的贡献
- [ ] 不生成泛化游戏设计建议 — 所有反馈都与提供的支柱词汇相关联
- [ ] 识别是否有任何支柱与该机制产生张力并以具体顾虑标记

## 协议合规性

- [ ] 仅使用 APPROVED / NEEDS REVISION 词汇返回裁决
- [ ] 停留在声明的游戏设计领域内
- [ ] 在未解决时将设计 vs. 公式冲突升级到 creative-director
- [ ] 不做出有约束力的代码实现、视觉艺术或独立叙事设定决策
- [ ] 提供可操作的设计反馈，而非实现规定

---

## 覆盖说明
- 经济设计审查（资源产出点、消耗点、通胀预防）未涵盖 — 应添加专用案例。
- 进度系统审查（XP 曲线、解锁门、玩家力量轨迹）未涵盖。
- 跨多个互联系统的核心循环验证（而非仅单个机制）未涵盖 — 推迟到 /review-all-gdds 集成。
- 与 systems-designer 关于公式所有权边界的协调协议可受益于额外案例。
