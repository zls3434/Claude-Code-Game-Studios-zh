## 阶段 1：理解任务

从参数中读取任务描述。如果描述太模糊而无法有意义的估算，在继续之前请求澄清。

读取 CLAUDE.md 了解项目背景：技术栈、编码规范、架构模式以及任何估算指南。

如果任务与已文档化的功能或系统相关，从 `design/gdd/` 中读取相关设计文档。

---

## 阶段 2：扫描受影响的代码

确定需要更改的文件和模块：

- 评估复杂度（大小、依赖数量、圈复杂度）
- 确定与其他系统的集成点
- 检查受影响区域现有的测试覆盖率
- 从 `production/sprints/` 中读取类似已完成任务的过往冲刺数据以及历史速度

---

## 阶段 3：分析复杂度因素

**代码复杂度：**
- 受影响文件中的代码行数
- 依赖项数量和耦合程度
- 是否涉及核心/引擎代码 vs 叶子/功能代码
- 是否可以遵循现有模式还是需要新模式

**范围：**
- 涉及的系统数量
- 新代码 vs 修改现有代码
- 所需新增的测试覆盖率
- 所需的数据迁移或配置更改

**风险：**
- 新技术或不熟悉的库
- 不清晰或模糊的需求
- 对未完成工作的依赖
- 跨系统集成的复杂度
- 性能敏感性

## 阶段 4：生成估算

```markdown
## 任务估算：[任务名称]
生成时间：[日期]

### 任务描述
[用 1-2 句话清晰地重述任务]

### 复杂度评估

| 因素 | 评估 | 备注 |
|--------|-----------|-------|
| 受影响的系统 | [列表] | [核心、游戏玩法、UI 等] |
| 可能修改的文件 | [数量] | [关键文件如下所列] |
| 新代码 vs 修改 | [比例] | |
| 集成点 | [数量] | [哪些系统交互] |
| 所需测试覆盖率 | [低 / 中 / 高] | |
| 可用的现有模式 | [是 / 部分 / 否] | |

**可能受影响的关键文件：**
- `[path/to/file1]` -- [此处将发生什么变化]

### 工作量估算

| 场景 | 天 | 假设 |
|----------|------|------------|
| 乐观 | [X] | 一切顺利，没有意外 |
| 预期 | [Y] | 正常节奏，小问题，一次审查 |
| 悲观 | [Z] | 出现重大未知因素，阻塞一天 |

**推荐预算：[Y 天]**

### 置信度：[高 / 中 / 低]

[解释哪些因素驱动了此特定任务的置信度等级。]

### 风险因素

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|-----------|--------|------------|

### 依赖关系

| 依赖项 | 状态 | 如果延迟的影响 |
|-----------|--------|-------------------|

### 建议分解

| # | 子任务 | 估算 | 备注 |
|---|----------|----------|-------|
| 1 | [调研 / 试探] | [X 天] | |
| 2 | [核心实现] | [X 天] | |
| 3 | [测试和验证] | [X 天] | |
| | **总计** | **[Y 天]** | |

### 备注和假设
- [影响估算的关键假设]
- [关于范围边界的任何注意事项]
```

输出估算并附带简要摘要：推荐预算、置信度等级以及最大的单一风险因素。

本 Skill 是只读的——不写入文件。裁决：**完成**——估算已生成。

---

## 阶段 5：后续步骤

- 如果置信度为低：建议在提交前进行有时间限制的试探（`/prototype`）。
- 如果任务超过 10 天：建议通过 `/create-stories` 将其分解为更小的故事。
- 要安排任务：运行 `/sprint-plan update` 将其添加到下一个冲刺中。

### 准则

- 始终给出范围（乐观 / 预期 / 悲观），从不给出单一数字
- 推荐预算应为预期估算，而不是乐观估算
- 四舍五入到半天增量——对于超过一天的任务，按小时估算意味着虚假的精度
- 不要无声地填充估算——明确地指出风险，以便团队可以做出决策
