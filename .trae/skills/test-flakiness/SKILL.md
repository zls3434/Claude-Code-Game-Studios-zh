# 测试不稳定性检测

不稳定测试是指有时通过、有时失败但没有代码变更的测试。在某些方面，不稳定测试比没有测试更糟——它们训练团队忽略红色 CI 运行结果，掩盖真正的失败。此 Skill 识别它们，解释可能的原因，并推荐对每个进行隔离还是修复。

**输出：** 更新 `tests/regression-suite.md` 隔离部分 + 可选 `production/qa/flakiness-report-[date].md`

**何时运行：**
- 打磨阶段（测试已运行多次；统计信号可靠）
- 当开发者开始将 CI 失败归因于"可能不稳定"时
- 在 `/regression-suite` 识别出需要诊断的隔离测试后

---

## 1. 解析参数

**模式：**
- `/test-flakiness [ci-log-path]` — 分析特定的 CI 运行日志文件
- `/test-flakiness scan` — 扫描 `.github/` 或标准日志输出目录中所有可用的 CI 日志
- `/test-flakiness registry` — 读取已有 regression-suite.md 隔离部分并提供已知不稳定测试的修复指导
- 无参数 — 自动检测：如果 CI 日志可访问则运行 `scan`，否则运行 `registry`

---

## 2. 定位 CI 日志数据

### 选项 A — GitHub Actions（首选）

检查测试结果产物：
```bash
ls -t .github/ 2>/dev/null
ls -t test-results/ 2>/dev/null
```

对于 Godot 项目：GdUnit4 输出与 JUnit 格式兼容的 XML 结果。
检查 `test-results/` 中的 `.xml` 文件。

对于 Unity 项目：game-ci 测试运行器默认输出 NUnit XML 到 `test-results/`。

对于 Unreal 项目：自动化日志输出到 `Saved/Logs/`。Grep 查找 `Result: Success` 和 `Result: Fail` 模式。

### 选项 B — 本地日志文件

如果提供了路径参数，直接读取该文件。

### 选项 C — 无可用日志数据

如果未找到日志：
> "未找到 CI 日志数据。要检测不稳定测试，此 Skill 需要来自多次运行的测试结果历史。选项：
> 1. 至少运行 3 次测试套件并收集输出日志
> 2. 检查 CI 流水线输出并将日志保存到 `test-results/`
> 3. 运行 `/test-flakiness registry` 审查已在 `tests/regression-suite.md` 中标记为不稳定的测试"

停止并询问用户选择哪个选项。

---

## 3. 解析测试结果

对于找到的每个 CI 日志或结果文件，解析：

**JUnit XML 格式**（GdUnit4 / Unity）：
- Grep `<testcase name=` 获取测试名称
- Grep `<failure` 或 `<error` 识别失败
- 解析 `classname` 和 `name` 属性获取完整测试标识符

**纯文本日志**：
- Grep 通过/失败模式：
  - Godot：测试名称旁边的 `PASSED` / `FAILED`
  - Unreal：`Result: Success` / `Result: Fail`
  - Unity：`Test passed` / `Test failed`

构建表格：`test_id → [run1_result, run2_result, run3_result, ...]`

---

## 4. 识别不稳定测试

如果测试在多次运行结果历史中同时出现 PASS 和 FAIL 结果，且运行之间无代码变更，则该测试是**不稳定的**。

不稳定性阈值：
- **高不稳定性**：超过 25% 的运行中失败 — 立即隔离
- **中等不稳定性**：5–25% 的运行中失败 — 调查并尽快修复
- **低/疑似不稳定性**：1–5% 的运行中失败 — 监控；可能是真正的罕见失败

对每个不稳定测试，分类可能的原因：

### 原因分类

| 原因 | 症状 | 修复方向 |
|-------|----------|---------------|
| **时序/异步** | 在等待信号或计时器后失败；通过率与系统负载相关 | 添加显式 await/同步；避免基于时间的延迟 |
| **顺序依赖** | 在特定其他测试之后运行时失败；单独运行时通过 | 添加适当的 setup/teardown；确保测试隔离 |
| **随机种子** | 无规律地间歇性失败；涉及 RNG | 传入显式种子；不要在测试中使用 `randf()` |
| **资源泄漏** | 在测试运行的后期更频繁失败 | 修复 teardown 中的清理；检查孤儿节点（Godot）或对象释放（Unity） |
| **外部状态** | 当来自先前测试的文件、场景或全局变量存在时失败 | 将测试与文件系统隔离；使用内存模拟 |
| **浮点数** | 在 `== 0.5` 等比较中失败 | 使用 epsilon 比较（`is_equal_approx`、`Assert.AreApproximately`） |
| **场景/预制体加载竞态** | 场景尚未就绪时失败 | 实例化后等待一帧；使用 `await get_tree().process_frame` |

使用 Grep 检查测试文件中是否有时序调用、randf、全局状态访问或浮点相等比较，以缩小原因范围。

## 5. 推荐行动

对于每个不稳定测试：

**隔离（高不稳定性）：**
> "立即隔离此测试。通过添加 `@pytest.mark.skip` / `[Ignore]` / `GdUnitSkip` 注解在 CI 中禁用它。将其记录到 `tests/regression-suite.md` 隔离部分。该测试现在是仅可选运行的。在移除隔离前修复根本原因。"

**调查并尽快修复（中等不稳定性）：**
> "此测试间歇性不可靠。根本原因可能是 [原因]。建议修复：[基于原因分类的具体修复]。暂时不要隔离——直接修复测试。"

**监控（低/疑似不稳定性）：**
> "此测试显示疑似不稳定性。在隔离前收集更多运行数据。在回归套件中将其记录为'疑似'。"

## 6. 生成报告

### 对话内摘要

```
## 不稳定性检测结果

**已分析运行次数**：[N]
**已跟踪测试数**：[N]

### 发现的不稳定测试

| 测试 | 系统 | 失败率 | 可能原因 | 推荐 |
|------|--------|-----------|--------------|----------------|
| [test_name] | [system] | [N]% | 时序 | 隔离 + 修复异步 |
| [test_name] | [system] | [N]% | 浮点比较 | 修复：使用 epsilon 比较 |
| [test_name] | [system] | [N]% | 顺序依赖 | 调查 teardown |

### 清洁测试（未检测到不稳定性）

[N] 个测试在 [N] 次运行中结果一致 — 未检测到不稳定性。

### 数据局限性

[如果可用运行次数少于 5 次则注明 — 运行次数越少，统计置信度越低]
```

## 7. 更新回归套件 + 可选报告文件

询问："我可以使用发现的不稳定测试更新 `tests/regression-suite.md` 的隔离部分吗？"

如果是：使用 `Edit` 将条目追加到隔离测试表。
绝不移除已有隔离条目 — 仅添加新的。

另行询问："我可以将完整不稳定性报告写入 `production/qa/flakiness-report-[date].md` 吗？"

完整报告包含每个测试的原因详情和引擎特定的修复代码片段。

写入后：

- 对于每个隔离测试："添加引擎特定的跳过注解以在 CI 中禁用此测试。根本原因修复后重新启用。"
- 对于适合修复的测试："[测试] 的修复很简单 — 将第 [N] 行的相等比较改为使用 `is_equal_approx`。"
- 摘要："一旦所有隔离注解都已应用，CI 应绿色通过。在发布关卡前为 [N] 个隔离测试排期修复工作。"

---

## 协作协议

- **绝不删除测试文件** — 隔离意味着注解 + 列入清单，而非移除
- **统计置信度很重要** — 运行次数少于 3 时，将发现标记为"疑似"而非"已确认"；询问是否有更多运行数据可用
- **修复始终是目标** — 隔离是临时的；即使推荐隔离也要指出修复方向
- **写入前询问** — 回归套件更新和报告文件都需要明确批准。写入时：判定：**COMPLETE** — 不稳定性报告已写入。拒绝时：判定：**BLOCKED** — 用户拒绝写入。
- **CI 中的不稳定性是团队问题** — 清晰地列出清单和推荐行动；不要仅在团队不知情的情况下静默隔离
