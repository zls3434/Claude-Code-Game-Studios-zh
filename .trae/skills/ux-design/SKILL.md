# UX 设计

此 Skill 以玩家为中心创作 UX 规格，从游戏设计中捕捉接口屏幕、HUD 或交互模式的需求。

**输出：** `design/ux/` 中的 UX 规格文档

---

## 第 0 阶段：确定设计什么

功能参数决定交互模式和要使用的模板。

**子命令：**

- `/ux-design [feature name]` → 对该功能运行完整的设计流程（第 1-9 阶段）
- `/ux-design hud` → 专注于 HUD。使用 `hud-design.md` 模板并运行第 1-3 阶段，然后跳转到第 7-9 阶段进行 HUD 设计流程和审查。
- `/ux-design patterns` → 运行交互模式设计流程（第 1 阶段然后第 10 阶段）。

**无参数：** 通过 `AskUserQuestion` 询问用户想设计什么：
- Prompt："你想设计哪个 UI 屏幕或功能？"
- Options：
  - `[A] 屏幕：主菜单 / 开始画面`
  - `[B] 屏幕：设置 / 选项菜单`
  - `[C] 屏幕：HUD / 玩法叠加`
  - `[D] 屏幕：物品栏或管理屏幕`
  - `[E] 屏幕：暂停菜单`
  - `[F] 屏幕：其他（请描述）`
  - `[G] 设计交互模式库（标准控件和模式）`

---

## 第 1 阶段：加载上下文

在设计任何东西之前，必须读取并综合：

- `design/gdd/game-concept.md` — 游戏类型、类型、平台、目标受众
- 此屏幕/功能的所有相关 GDD 部分（例如，对于物品栏屏幕，加载物品栏 GDD 及其 UI Requirements 部分）
- `.claude/docs/technical-preferences.md` — 平台和输入配置
- `design/player-journey.md`（如果存在）— 到达此屏幕时的玩家状态和背景
- `design/ux/interaction-patterns.md`（如果存在）— 已有的模式；复用，不要重新发明
- `design/accessibility-requirements.md`（如果存在）— 无障碍承诺等级

**如果 `design/ux/interaction-patterns.md` 缺失且用户正在设计除模式库之外的内容**：在简报中注明"无模式库 — 所有模式将被视为此项目的新模式"，并在最终摘要中建议用户运行 `/ux-design patterns`。继续设计而不阻塞。

**综合成设计简报：**
- 这是个什么屏幕？
- 玩家到达时处于什么状态？（刚结束战斗？刚加载存档？）
- 玩家来到此时需要完成什么任务？
- 有什么约束？（平台、输入方法、性能、无障碍等级）
- 什么已有模式是相关的？

---

## 第 2 阶段：玩家需求定义

在设计任何 UI 结构之前：

1. 定义玩家视角的目标："当玩家打开此屏幕时，他们想要______"
2. 确定成功的衡量标准："玩家在少于 [N] 个操作内找到他们需要的内容"
3. 识别关键玩家任务（不是系统任务——玩家在做什么）
4. 列出在流程中可能发生的玩家错误

不要从 UI 结构开始——从玩家开始。

---

## 第 3 阶段：信息架构

建立屏幕的信息结构：

- 什么信息对玩家最重要？（视觉层次）
- 什么信息是次要的？
- 什么信息可以隐藏或按需访问？
- 信息之间如何关联？（分组、排序）
- 默认状态是什么？空状态呢？

---

## 第 4 阶段：流程和导航设计

设计玩家如何到达、在此停留、以及离开：

- **进入点**：玩家从哪些屏幕/状态可以到达此处？
- **退出点**：玩家可以前往哪些屏幕/状态？
- **返回行为**：在游戏玩法和屏幕之间切换时，"返回"按钮做什么？
- **导航位置**：此屏幕在屏幕层级中的位置？

---

## 第 5 阶段：布局和线框图

设计屏幕的物理布局。使用 ux-spec.md 模板并以文本形式描述布局：

**布局部分：**
- 区域（例如 头部、内容、页脚）
- 组件（例如 按钮、列表、输入）
- 组件清单表（组件名称、区域、规格引用、状态、备注）

**状态和变体：**
- 加载状态（数据加载中）
- 空状态（无数据）
- 错误状态（出了什么问题）
- 变体（例如 不同玩家的物品栏布局相同但内容不同）

**动画/过渡：**
- 进入动画（屏幕如何出现）
- 退出动画（屏幕如何消失）
- 过渡（此屏幕内的微交互）

---

## 第 6 阶段：交互设计

为所有交互定义完整的行为规格，覆盖所有目标输入方法。使用 `.claude/docs/technical-preferences.md` 中的配置确定要覆盖哪些输入方法。

你的规格必须记录每个交互的鼠标、键盘、手柄和触摸行为（取决于平台）。

**平台覆盖要求：**
- **PC**：记录鼠标点击/悬停 + 键盘（Tab 导航、Enter/空格选择、Escape 返回）
- **主机**：记录手柄按钮 + D-pad 导航 + 模拟摇杆行为
- **移动端**：记录触摸/拖拽/滑动手势、长按、多点触控
- **多平台**：所有适用方法完全记录

**交互元素：**
- 焦点顺序（Tab 导航、手柄 d-pad）
- 按钮：点击/按下的行为，长按（如适用）
- 列表/网格：滚动、选择、多选
- 模态/覆盖层：打开行为、关闭行为、焦点陷阱
- 可拖动元素：（如适用）
- 键盘快捷键（如有，在键盘支持中记录）

**事件说明：**
- 屏幕为每个玩家动作触发 UI 事件
- 接收系统为每个玩家动作触发状态响应
- UI 无法修改游戏状态——仅显示

**错误处理：**
- 输入验证：无效输入时发生什么
- 错误消息：显示位置和方式
- 恢复：玩家如何从错误中恢复
- 玩家撤销意外动作的能力

---

## 第 7 阶段：数据需求

对于此屏幕显示的每个数据元素：

- 数据是什么？显示什么信息？
- 数据来源：它来自哪个游戏系统？
- 更新频率：变化频率如何？（每帧、每秒、仅在状态变更时、按需加载）
- **绝不将 UI 列为任何数据的"所有者"**
- 实时数据指定触发：什么事件导致此值更新？

---

## 第 8 阶段：无障碍

级别应从 `accessibility-requirements.md` 读取。如果该文件不存在，默认至少达到 Basic：
- 无仅靠颜色传达信息（所有颜色编码必须有色盲友好的替代方案）
- 所有文本与背景对比度至少达到 4.5:1
- 所有屏幕的导航顺序连贯

对于更高等级，添加：
- Standard：纯键盘导航完全记录、文本调整大小、音频提示
- Comprehensive：屏幕阅读器支持、动效减少、完全可重映射的控制、认知无障碍

---

## 第 9 阶段：最终 UX 规格文档

遵循 `ux-spec.md` 模板（或 `hud-design.md`，如果设计 HUD）。

**HUD 特殊处理：** 如果正在设计 HUD，使用 `hud-design.md` 模板，该模板以规格哲学和视觉预算开始——定义 HUD 在游戏体验中扮演的角色以及最大同时元素限制。之后为个体元素进行设计。

呈现完整的 UX 规格。

运行自己的 QA 审查：
- 每个部分是否完整？
- 是否所有交互都已记录？
- 是否覆盖了所有输入方法？
- 是否定义了状态（加载中、空、错误）？
- 是否指定了数据来源？
- 是否满足了无障碍要求？

询问用户："我可以将此 UX 规格写入 `design/ux/[feature-name].md` 吗？"

在写入前等待批准。判定：**COMPLETE** — UX 规格已创建。

如果拒绝，在此停止。判定：**BLOCKED** — 用户拒绝写入。

写入后，呈现：
```
UX 规格已写入 `design/ux/[feature-name].md`。

后续步骤：
- 运行 /ux-review design/ux/[feature-name].md 验证完整性和一致性
- 或运行 /team-ui [feature-name] 通过完整实现管线处理此屏幕
- 如果出现新的交互模式，运行 /ux-design patterns 将其添加到库中
```

---

## 第 10 阶段：交互模式设计（`/ux-design patterns`）

当目标为交互模式库时：

1. 加载 `design/ux/interaction-patterns.md`（如果存在）
2. 审查所有 GDD 的 UI Requirements 部分以收集所有必需的交互模式
3. 对于每种模式类型，定义：
   - 何时使用此模式 vs. 何时不使用
   - 完整状态规格（默认、悬停、按下、禁用、聚焦）
   - 无障碍规格（键盘、屏幕阅读器、颜色）
   - 实现说明（组件类型、属性）
4. 编译动画标准表（持续时间、缓动、用途）
5. 编译声音标准表（事件、用途）
6. 保存到 `design/ux/interaction-patterns.md`

**关键模式：** 对每个新模式的 When to Use / When NOT to Use 部分给予同等重视。阻止不当使用与启用正确使用同样重要。

询问："我可以将此模式库写入 `design/ux/interaction-patterns.md` 吗？"

写入前等待批准。判定：**COMPLETE** — 模式库已创建/更新。

---

## 协作协议

- **等待批准再写入** — 第 9 和 10 阶段需要明确批准才能写入文件
- **在实现中呈现结果** — 所有内容首先可视到对话中
- **从玩家开始** — 绝不在定义用户需求前设计 UI
- **记录所有输入方法之间的交互** — 不要假设"键鼠仅 PC"或"仅触摸移动端"——阅读项目配置并相应记录
