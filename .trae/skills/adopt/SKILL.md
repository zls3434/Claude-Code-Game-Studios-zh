# Adopt — 棕地模板适配

此技能审计现有项目的制品是否**格式合规**，以适配模板的技能流水线，然后生成优先级排序的迁移计划。

**这不是 `/project-stage-detect`。**
`/project-stage-detect` 回答：*存在什么？*
`/adopt` 回答：*存在的东西是否能与模板的技能实际协同工作？*

一个项目可以有 GDD（游戏设计文档）、ADR（架构决策记录）和用户故事 — 但如果这些制品使用了错误的内部格式，每个对格式敏感的技能仍会悄无声息地失败或产生错误结果。

**输出：** `docs/adoption-plan-[date].md` — 一份持久、可核对的迁移计划。

**参数模式：**

**审计模式：** `$ARGUMENTS[0]`（空白 = `full`）

- **无参数 / `full`**：完整审计 — 所有制品类型
- **`gdds`**：仅 GDD 格式合规性
- **`adrs`**：仅 ADR 格式合规性
- **`stories`**：仅故事格式合规性
- **`infra`**：仅基础设施制品差距（注册表、清单、冲刺状态、阶段文件）

## 阶段 1：检测项目状态

在开始读取前输出一行：`"正在扫描项目制品..."` — 这确认技能在静默读取阶段正在运行。

然后在呈现任何其他内容之前静默读取。

### 存在性检查
- `production/stage.txt` — 如果存在，读取它（权威的阶段文件）
- `design/gdd/game-concept.md` — 概念文档存在？
- `design/gdd/systems-index.md` — 系统索引存在？
- 统计 GDD 文件数量：`design/gdd/*.md`（排除 game-concept.md 和 systems-index.md）
- 统计 ADR 文件数量：`docs/architecture/adr-*.md`
- 统计故事文件数量：`production/epics/**/*.md`（排除 EPIC.md）
- `.claude/docs/technical-preferences.md` — 引擎已配置？
- `docs/engine-reference/` — 引擎参考文档存在？
- Glob `docs/adoption-plan-*.md` — 如果有任何已存在的计划，记录最近一个计划的文件名

### 推断阶段（如果没有 stage.txt）
使用与 `/project-stage-detect` 相同的启发式方法：
- `src/` 中有 10+ 个源文件 → 生产阶段
- `production/epics/` 中有故事 → 预生产阶段
- ADR 存在 → 技术设计阶段
- systems-index.md 存在 → 系统设计阶段
- game-concept.md 存在 → 概念阶段
- 什么都没有 → 全新的（不是棕地项目 — 建议使用 `/start`）

如果项目看起来是全新的（完全没有制品），使用 `AskUserQuestion`：
- "这看起来是一个全新项目 — 没有找到已有的制品。`/adopt` 适用于已有工作需要迁移的项目。您想做什么？"
  - "运行 `/start` — 开始引导式首次上线"
  - "我的制品在非标准位置 — 帮我找到它们"
  - "取消"

然后停止 — 无论用户选择哪个选项，都不要继续审计（每个选项指向不同的技能或人工调查）。

报告："检测到阶段：[阶段]。找到：[N] 个 GDD，[M] 个 ADR，[P] 个故事。"

## 阶段 2：格式审计

对于范围内（基于参数模式）的每种制品类型，不仅检查文件是否存在，还要检查它是否包含模板所要求的内部结构。

### 2a：GDD 格式审计

对于找到的每个 GDD 文件，通过扫描标题检查 8 个必需部分：

| 必需部分 | 标题匹配模式 |
|---|---|
| 概述 | `## 概述` 或 `## Overview` |
| 玩家幻想 | `## 玩家幻想` 或 `## Player Fantasy` |
| 详细规则 / 设计 | `## 详细` 或 `## 核心规则` 或 `## Detailed` 或 `## Core Rules` |
| 公式 | `## 公式` 或 `## Formulas` 或 `## Formula` |
| 边界情况 | `## 边界情况` 或 `## Edge Cases` |
| 依赖项 | `## 依赖项` 或 `## Dependencies` 或 `## Depends` |
| 调优参数 | `## 调优` 或 `## Tuning` |
| 验收标准 | `## 验收` 或 `## Acceptance` |

对于每个 GDD，记录：
- 哪些部分存在
- 哪些部分缺失
- 存在的部分是否有实际内容还是只是占位文本（`[待设计]` 或等效内容）

同时检查：每个 GDD 在其头部块中是否有 `**状态**：` 或 `**Status**：` 字段？
有效值：`设计中`、`已设计`、`审核中`、`已批准`、`需修订`（或 `In Design`、`Designed`、`In Review`、`Approved`、`Needs Revision`）。

### 2b：ADR 格式审计

对于找到的每个 ADR 文件，检查这些关键部分：

| 部分 | 缺失时的影响 |
|---|---|
| `## 状态` 或 `## Status` | **阻塞级** — `/story-readiness` 的 ADR 状态检查会静默通过所有内容 |
| `## ADR 依赖项` 或 `## ADR Dependencies` | 高 — `/architecture-review` 中的依赖排序会中断 |
| `## 引擎兼容性` 或 `## Engine Compatibility` | 高 — 截止日期后的 API 风险未知 |
| `## GDD 需求覆盖` 或 `## GDD Requirements Addressed` | 中 — 可追溯性矩阵丢失覆盖 |
| `## 性能影响` 或 `## Performance Implications` | 低 — 非流水线关键项 |

对于每个 ADR，记录：哪些部分存在，哪些部分缺失，如果 Status 部分存在则记录当前的 Status 值。

### 2c：systems-index.md 格式审计

如果 `design/gdd/systems-index.md` 存在：

1. **带括号的状态值** — Grep 查找任何包含括号的 Status 单元格：
   `"需修订 ("`、`"进行中 ("` 等。
   这些会破坏 `/gate-check`、`/create-stories` 和 `/architecture-review` 中的精确字符串匹配。**阻塞级。**

2. **有效的状态值** — 检查 Status 列的值是否仅来自：
   `未开始`、`进行中`、`审核中`、`已设计`、`已批准`、`需修订`
   （或 `Not Started`、`In Progress`、`In Review`、`Designed`、`Approved`、`Needs Revision`）
   标记任何无法识别的值。

3. **列结构** — 检查表格至少包含：系统名称、层级、优先级、状态列。缺少列会降低技能功能。

### 2d：故事格式审计

对于找到的每个故事文件：

- **`清单版本：`（`Manifest Version:`）字段** — 故事头部是否存在？（低 — 如果不存在则自动通过）
- **TR-ID 引用** — 故事是否包含 `TR-[a-z]+-[0-9]+` 模式？（中 — 无过期跟踪）
- **ADR 引用** — 故事是否引用至少一个 ADR？（检查 `ADR-` 模式）
- **状态字段** — 存在且可读？
- **验收标准** — 故事是否有复选框列表（`- [ ]`）？

### 2e：基础设施审计

| 制品 | 路径 | 缺失时的影响 |
|---|---|---|
| TR 注册表 | `docs/architecture/tr-registry.yaml` | 高 — 无稳定的需求 ID |
| 控制清单 | `docs/architecture/control-manifest.md` | 高 — 故事没有层级规则 |
| 清单版本戳 | 清单头部：`清单版本：`（`Manifest Version:`） | 中 — 过期检查失效 |
| 冲刺状态 | `production/sprint-status.yaml` | 中 — `/sprint-status` 回退到 markdown |
| 阶段文件 | `production/stage.txt` | 中 — 阶段自动检测不可靠 |
| 引擎参考 | `docs/engine-reference/[engine]/VERSION.md` | 高 — ADR 引擎检查失效 |
| 架构可追溯性 | `docs/architecture/architecture-traceability.md` | 中 — 无持久化矩阵 |

### 2f：技术偏好审计

读取 `.claude/docs/technical-preferences.md`。检查每个字段是否有 `[待配置]`（`[TO BE CONFIGURED]`）：
- 引擎、语言、渲染、物理 → 如果未配置则为高（ADR 技能失败）
- 命名规范 → 中
- 性能预算 → 中
- 禁止模式、允许的库 → 低（设计上以空值开始）

## 阶段 3：分类和优先级排序差距

将跨所有审计找到的每个差距组织成四个严重级别：

**阻塞级（BLOCKING）** — 将导致模板技能*立即*静默产生错误结果。
示例：ADR 缺少 Status 字段，systems-index 包含带括号的状态值，存在 ADR 但引擎未配置。

**高（HIGH）** — 将导致生成的故事缺少安全检查，或基础设施引导会失败。
示例：ADR 缺少引擎兼容性，GDD 缺少验收标准（无法从中生成故事），tr-registry.yaml 缺失。

**中（MEDIUM）** — 降低质量和流水线跟踪能力，但不破坏功能。
示例：GDD 缺少调优参数或公式部分，故事缺少 TR-ID，sprint-status.yaml 缺失。

**低（LOW）** — 追溯性改进，有则更好但不紧急。
示例：故事缺少清单版本戳，GDD 缺少开放问题部分。

统计每个级别的总数。如果零个阻塞级和零个高差距：报告项目是模板兼容的，仅剩建议性改进。

## 阶段 4：构建迁移计划

编写一个编号、有序的行动计划。排序规则：
1. 阻塞级差距优先（必须在任何流水线技能可靠运行之前修复）
2. 其次是高级别差距，基础设施在 GDD/ADR 内容之前（引导需要正确的格式）
3. 中级差距排序：GDD 差距在 ADR 差距之前，ADR 差距在故事差距之前（故事依赖于 GDD 和 ADR）
4. 低级差距最后

对于每个差距，生成一个计划条目，包含：
- 清晰的问题描述（一句话，无术语）
- 修复它的确切命令（如果某个技能可以处理）
- 如果需要直接编辑，则提供手动步骤
- 时间估算（粗略：5 分钟 / 30 分钟 / 1 个会话）
- 用于跟踪的复选框 `- [ ]`

**特殊情况 — systems-index 包含带括号的状态值：**
如果存在，此项始终是第一个。显示需要更改的确切值和精确的替换文本。在编写计划之前，提供立即修复此问题的选项。

**特殊情况 — ADR 缺少 Status 字段：**
对于每个受影响的 ADR，修复方法是：
`/architecture-decision retrofit docs/architecture/adr-[NNNN]-[slug].md`
将每个 ADR 列为单独的可核对待办项。

**特殊情况 — GDD 缺少部分：**
对于每个受影响的 GDD，列出缺少哪些部分以及修复方法：
`/design-system retrofit design/gdd/[filename].md`

**基础设施引导排序** — 始终按此顺序呈现：
1. 先修复 ADR 格式（注册表依赖于读取 ADR Status 字段）
2. 运行 `/architecture-review` → 引导生成 `tr-registry.yaml`
3. 运行 `/create-control-manifest` → 创建带有版本戳的清单
4. 运行 `/sprint-plan update` → 创建 `sprint-status.yaml`
5. 运行 `/gate-check [阶段]` → 权威写入 `stage.txt`

**已有故事** — 明确注明：
> "已有故事继续与所有模板技能协同工作 — 当字段不存在时，所有新格式检查自动通过。但它们不会从 TR-ID 过期跟踪或清单版本检查中受益，直到被重新生成。这是有意为之：不要重新生成已在进行中的故事。"

在请求写入之前，显示一个**差距预览**：
- 将每个阻塞级差距列为一行项目符号，描述实际问题

- 高/中/低级仅显示数量（例如 `高：4，中：2，低：1`）。

这给用户足够的上下文来判断范围，然后再决定是否写入文件。

如果在阶段 1 中检测到之前的适配计划，添加注释：
> "之前的计划存在于 `docs/adoption-plan-[prior-date].md`。新计划将反映当前项目状态 — 它不会与之前的运行结果进行差异对比。"

  - "先显示完整计划预览（暂不写入）"

如果用户选择"先显示完整计划预览"，将完整计划输出为围栏代码块。然后再次用相同的三个选项询问。

## 阶段 6b：设置审核模式

在写入适配计划后（或如果用户取消写入），检查 `production/review-mode.txt` 是否存在。

**如果存在**：读取并记录当前模式 — "审核模式已设置为 `[当前]`。" — 跳过提示。

**如果不存在**：使用 `AskUserQuestion`：

- **提示**："还有一个设置步骤：在您按工作流推进的过程中，希望获得多少设计审核？"
- **选项**：
  - `完整` — 在每个关键工作流步骤由总监专家审核。最适合团队、学习工作流，或当您希望对每个决策都有充分反馈时。
  - `精简（推荐）` — 仅在阶段关卡转换（/gate-check）时由总监审核。跳过每个技能的审核。对独立开发者和小团队而言是平衡的选择。
  - `单人` — 完全没有总监审核。速度最大化。最适合游戏 Jam、原型开发，或当审核感觉像是额外负担时。

选择后立即将选项写入 `production/review-mode.txt` — 无需单独的"可以写入吗？"：
- `完整` → 写入 `full`
- `精简（推荐）` → 写入 `lean`
- `单人` → 写入 `solo`

如果 `production/` 目录不存在，则创建它。

## 阶段 7：提供第一步行动

在写入计划后，不要就此停下。选择优先级最高的单个差距，并使用 `AskUserQuestion` 提供立即处理。选择第一个适用的分支：

**如果 systems-index.md 中存在带括号的状态值：**
使用 `AskUserQuestion`：
- "最紧急的修复是 `systems-index.md` — [N] 行包含带括号的状态值（例如 `需修订（参见备注）`），这会立即破坏 /gate-check、/create-stories 和 /architecture-review。我可以当场修复这些。"
  - "立即修复 — 编辑 systems-index.md"
  - "我自己修复"
  - "完成 — 给我计划就行"

**如果 ADR 缺少 `## Status`（且没有带括号的问题）：**
使用 `AskUserQuestion`：
- "最紧急的修复是向 [N] 个 ADR 添加 `## Status`：[列出文件名]。没有它，/story-readiness 会静默通过所有 ADR 检查。从 [第一个受影响的文件名] 开始？"
  - "是 — 现在改造 [第一个受影响的文件名]"
  - "逐一改造全部 [N] 个 ADR"
  - "我自己处理 ADR"

**如果 GDD 缺少验收标准（且以上没有阻塞级问题）：**
使用 `AskUserQuestion`：
- "最紧急的差距是 [N] 个 GDD 缺少验收标准：[列出文件名]。没有它们，/create-stories 无法生成故事。从 [优先级最高的 GDD 文件名] 开始？"
  - "是 — 现在向 [GDD 文件名] 添加验收标准"
  - "逐一处理全部 [N] 个 GDD"
  - "我自己处理 GDD"

**如果没有阻塞级或高级别差距：**
使用 `AskUserQuestion`：
- "没有阻塞级差距 — 此项目是模板兼容的。接下来做什么？"
  - "带我逐步完成中级改进"
  - "运行 /project-stage-detect 进行更广泛的健康检查"
  - "完成 — 我将按自己的节奏完成计划"

> **适配计划已保存到 `docs/adoption-plan-[date].md`。** 随时重新运行 `/adopt`，按完成后重新检查剩余差距。

## 协作协议

1. **静默读取** — 在呈现任何内容之前完成完整审计
2. **先显示摘要** — 让用户在请求写入之前看到范围
3. **写入前询问** — 始终在创建适配计划文件之前确认
4. **提供而非强制** — 计划是建议性的；用户决定修复什么以及何时修复
5. **一次一个行动** — 在交付计划后，提供一个具体的下一步行动，而不是同时列出六件事
6. **永不重新生成已有制品** — 只填补已有内容的差距；不要重写已有内容的 GDD、ADR 或故事
