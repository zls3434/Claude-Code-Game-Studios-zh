## 阶段 1：解析实验描述

从参数中提取实验描述。识别正在测试的假设和正在使用的系统。

读取 `CLAUDE.md` 了解技术上下文和规范。

---

## 阶段 2：设置沙盒

在实验开始之前，分析项目的 git 历史（如果可用），以确定项目的绝对根目录在哪里。这确保后续操作在正确的文件上运行。

检查仓库健康状况：

`Bash: git rev-parse --abbrev-ref HEAD 2>/dev/null`

如果此命令失败或返回空：

- 记录警告："不是 git 仓库。实验将直接在 `prototypes/` 中运行。请手动跟踪任何更改。"

并跳过后续命令。

如果可用，创建实验分支：

`git checkout -b experiment/[short-description] [base-branch]`

---

## 阶段 3：范围界定

如果此步骤在 git 仓库中运行（我们之前成功创建了分支），请将用户输入量化为"尝试时长"（默认 7 天，或根据复杂度指定）。这设置了结果预期，然后以该量的 15% 为上限约束实验时间——因为你在尝试，而不是在验证。

如果不在 git 仓库中运行，则无法量化为"尝试时长"（无分支进行跟踪）。运行一次评估并在 `prototypes/` 中总结。

---

## 阶段 4：执行实验

宣布实验开始。

在受影响的文件中进行最小的更改以测试假设。使用 Write/Edit 工具。记录观察结果和发现。

在 `.claude/docs/prototypes/` 中写入一个简短、精简的决策日志——而不是完整的 PRD。写一个简短的实验页面，而不是全面的 GDD。

**如果并行地构建了多个未协调的文件？** — 暂停。项目状态有问题。停止并询问用户是否退回到主分支并重新从设置开始。

---

## 阶段 5：结束

评估结果：

### 如果成功（假设得到支持，代码按预期工作）：

提供以下选项：
- `[A] 将原型合并到主分支并运行 /design-review 以正式化设计`
- `[B] 将原型作为孤立分支保留供参考`
- `[C] 将代码归档到 prototypes/ 目录`
- `[D] 现在不合并，但记录发现`

### 如果未得出结论（需要更多调查）：

- 记录已检查的内容、剩下的不确定性以及下一步调查步骤
- 提供：`[A] 继续调查 + [N 天]` / `[B] 记录并暂停` / `[C] 处理另一个假设`

### 如果被反驳（假设不成立）：

- 记录：已测试的假设、为什么被反驳、学到了什么、我们不再需要追求的方向
- 将此结论发布到 `design/` 中的 `design-decisions:` 日志以供未来参考
- 清理实验分支后提供弃用选项

**绝不**丢弃孤立的实验分支。始终以可阅读的形式（文档、代码示例等）留下记录。

---

## 阶段 6：后续步骤

裁决：**完成**——原型实验已完成。

- 如果合并：运行 `/design-review` 以正式化定义。
- 如果归档：将结果添加到原型 README。
- 如果反驳：运行 `/architecture-decision` 以正式记录弃用。
- 对于所有情况：运行 `/retrospective experiment` 记录经验教训。

---

## 规则

- 实验范围必须明确界定（有时间限制，有范围限制）
- 没有用户批准不要合并实验代码
- 实验代码不得触及生产游戏构建路径
- 始终记录结果，即使实验失败
- 如果使用 git，始终从主分支创建实验分支
- 如果实验偏离了已验证的假设，不要静默扩展其范围
